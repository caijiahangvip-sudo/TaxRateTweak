# TaxRateTweak 1.8.22 — 继续压稳态开销，并给需求重算加计时

1.8.22：

- **去掉周期性全城扫描**：实测一遍 **47ms**。原来暂停时每 30 秒一次、写档每 8192 帧一次，纯属浪费——税率变化走缓存重算（不扫描），税基只在游戏推进时才漂移，而每游戏日结算本来就会完整重扫一遍。现在只在"很久没刷新"（暂停 5 分钟 / 65536 帧）兜底一次。
- **拖免税线滑块的扫描节流从 250ms 放宽到 1 秒**：免税线会改变税基，必须重扫，但一遍 47ms，拖动时不能每次都付。
- **给需求重算加计时日志**：`Recalculate` 每 16 模拟帧跑一次（全城住宅地产扫描 + 5 个依赖同步点），是模组里唯一还没量化的开销。现在每分钟打一条：`需求重算耗时：最近一分钟 N 次，平均 Xms，最大 Yms`。

1.8.21 继续压稳态开销，三处：

- **幸福度注入量改由缓存重算**：平均附加税只依赖各档税率与住户数，现在拖动税率时立刻更新，不必等下一次全城扫描（这也让扫描可以放得很疏）。
- **稳态扫描从"暂停 3 秒 / 模拟 1024 帧"放宽到"暂停 30 秒 / 8192 帧"**：税率变化走缓存重算（不扫描），税基只在游戏推进时才漂移，而每游戏日结算本来就会完整重扫一遍。
- **需求 UI 绑定只在内容真的变化时才推送**：需求系统每 16 模拟帧重算并抬高 Revision，但数值按天变化；无脑推送等于每 0.25 秒让五类需求区块、工具栏需求条与图例重绘一遍。现在比较 64 位内容签名，不变就不推。

**仍然存在的开销（诚实列出）**：

- 每**游戏日**一次完整结算扫描（按人累加税基，量级几十毫秒）——这是真实收税所必需的。
- 每 16 模拟帧一次的**需求重算**（全城住宅地产扫描 + 若干同步点）——量级我还没实测，下一步加耗时日志，再决定动不动它。

# TaxRateTweak 1.8.18 — 幸福度改成与原版同公式、等比例

1.8.18 按要求去掉 1.8.17 里那道"±8 点预算 / ±50 个百分点"的截断：附加税现在被**等量当作有效住宅税率的抬升**，走原版同一套公式、同一灵敏度，只是税更大所以影响按比例更大。

- 修正量 = **负的人口加权平均附加税率（百分点）**，不再有任何上限或截断：附加税 +50% 就等同于"税率高了 50 个百分点"，附加税 −10% 就等同于"税率低了 10 个百分点"。
- 因此 50% 与 100% 的附加税不再被压成同一个值，影响严格与附加税成比例。
- 后果要清楚：−1000% 的补贴档会给出一个极大的幸福度加成（和把顶部税率设到 −1000% 是同一量级的现象，因为模组本来就允许那个范围）；数值不会溢出崩溃，只是市民幸福度会顶到上限。
- 日志仍打印中间量（平均附加税、生效偏移、学历系数），便于核对量级。

1.8.17 修掉 1.8.15 引入的一个数量级错误：幸福度那边算的是 `10 − 名义住宅税率`，税率和这个值都是**百分点**（10 表示 10%），而注入的修正量我按**分数**传了（0.11 而不是 11）。后果是影响只有应有的 1/100——把附加税设到 100%，实际只让有效税率上移 0.5 个百分点，幸福度当然只动一点点。

现在：

- 修正量改用百分点：附加税 100% → 有效税率上移 100 个百分点。
- 加了一道自校准上限：先按"最多让税收因素变化 ±8 点"反算允许的偏移百分点（用原版五个学历档税收系数的绝对值最大者换算，运行时读取，不猜资产数值），再钳到 ±50 个百分点以内。
- 日志打印全部中间量，便于核对：平均附加税百分比、生效偏移百分点、上限、学历系数最大绝对值。

1.8.16 把分密度附加税的税基改成**按人**算：对每个家庭成员各自取 `max(0, 个人收入 − 免税线)` 再求和，再乘该档附加率。

原因：原版的免征本来就是按人算的（`PayWageSystem` 对每个市民各减一次免税线），幸福度也是按人算的。此前模组按"户收入 − 免税线"只减一次，多职工家庭会比原版口径多缴。

- 个人收入口径与原版一致：有工作者取该学历档工资；儿童/青少年取家庭津贴、老人取养老金、其余取失业救济（原版这些同样参与免征扣除）。
- 两处刻意不判：死亡市民（原版会跳过）与失业补助的领取天数上限——影响仅限当天的微小偏差。拿不到成员表时退回按户口径。
- 代价：一遍预估变重，所以暂停时的稳态刷新从 1 秒放宽到 3 秒（设置变化后仍约一帧刷新）。
- 刻意不对 `Worker` / `Citizen` 调同步点：那会阻塞在市民更新作业上，宁可数字略偏也不要停顿。

1.8.15 让五档附加税影响原版的"税收"幸福度因素。原版那个因素算的是 `10 − 名义住宅税率`，再乘学历系数、按人口加权平均；城市实体上的 `CityModifier` 第 40 项（TaxHappiness）正好是对 `10 − 税率` 的一个修正，等价于"给所有人的名义税率加同一个数"。

- 注入量 = **负的人口加权平均附加税**，钳制在 −30% ~ +50%（防止 −1000% 的补贴档变成无限幸福加成）。
- 一个标量就够：公式对税率是线性的，学历系数只依赖学历、附加税只依赖住房密度，两者线性可分，所以 5 学历 × 5 密度的 25 格会塌缩成一个加权平均。这是在"学历与住房密度不相关"假设下的精确实现；要按学历分别给不同值必须改后台 Burst 作业的机器码，不做。
- 与附加税开关同生共死：关掉分密度附加税即自动撤掉幸福度影响。
- 该缓冲区由游戏的策略流程整块 `Clear()` + 重算，所以注入每帧在"重建之后、幸福度读取之前"补写一次，并用"当前值 ≠ 上次写入值"把游戏自己那份认出来，避免叠加。
- 生效时日志会打印 `分密度附加税已接入税收幸福度：…（税收因素现值 …）`，可据此确认是否真的被幸福度系统采纳。

1.8.14 修掉一个会把金库掏空的行为。免税线此前带了"负所得税"：低于免税线的家庭会按差额**领取补贴**。而免税线滑块能设到 50000，住户日均收入却只有几千——于是这个补贴变成按"免税线 × 附加率"给全城发钱（约 5 万户 × 5000 ≈ 2.5 亿/日），城市金库瞬间被抽干。

现在：

- 税基 = `max(0, 昨日工资 − 免税线)`；低于免税线的部分应缴 **0**，不收也不发。
- 免税线是**全免税**：它同时免掉基础住宅税和分密度附加税——因为它就是原版那个"税前扣除额"参数，原版自己按"(工资 − 免税线) × 税率"征税，所以低于线的部分本来就不缴基础税；模组这一侧的附加税税基现在也把下限设为 0。
- 免税线只负责免征，与补贴彻底解耦。
- 负附加税率（玩家主动把某一行设成负数）仍按原设计给住户发钱——那是显式设置，不受本次改动影响。
- 政策描述在全部 12 种语言里改为"基础住宅税和附加税一起免征，只免征不发放补贴"。

1.8.13 修掉一个会误导玩家的显示口径。五档密度税行原来显示 `基础住宅税率 + 附加税`，而模组只收附加那部分。于是默认状态（顶部住宅 10%、附加 0%）下行数字写着 10%，实际附加收入是 0——看起来就像"附加税收不上来"。

更早的 1.8.7–1.8.10 是按 `基础 + 附加` 征收的，等于把基础住宅税再收一遍（住户多付一份、城市多收一份），而行数字仍显示 10%，两头都对不上。

现在：

- 行数字 = 该档**附加税率本身**；收多少就显示多少，与"预估"列同口径。
- 该档住户的合计住宅税率 = **顶部住宅税率 + 该行数字**；基础部分由原版 `TaxSystem` 征收，模组不重复收。
- 因此顶部住宅税率变化时这五行不再跟着动（它们只表示额外加收的部分）。
- 五档附加税全为 0 时补一条日志说明"本模组不征收附加税"；存档恢复日志补上启用开关。

1.8.12 改了免税线政策的语义，并让整条链路可追溯：

- **勾选** → 阈值 = 滑块值。
- **未勾选** → 阈值 = 0（不设免征线，全部工资计入应税收入）。此前未勾选是"恢复原版免税线"，于是滑块在未勾选时完全无效——这正是"免税线什么用都没有"的来源。
- 阈值 0 等于取消原版那条平衡用免征额（原版值 1000），效果与把滑块拉到最左端一致。
- 日志三段全部无条件记录：政策状态（含未勾选时滑块值不生效的限流提示）→ 阈值写入经济参数 → 写入校验。
- 仅在政策条目存在时接管；玩家从未动过该政策时不碰设置，沿用原版值。

1.8.11 只收附加税：1.8.7–1.8.10 把"基础住宅税率 + 附加税"当成结算税率，但原版 `TaxSystem.PayTax` 已经按同一税基从住户钱包扣过基础住宅税，导致同一笔基础税被收两次（住户付两次、城市收两次）。现在结算与福利门槛只用附加税，面板行仍显示"基础 + 附加"。

同一版还修掉这几处：

- 关闭免税线政策会真正还原原版值（此前只写不还原，免税线会一直生效到下次读档）。
- 预估与实收统一从同一个来源读免税线；此前预估读设置、实收读经济参数，两者一旦不同就会悄悄分叉。
- 免税线写入做一次落地校验并记日志（含"写入未生效"的 WARN），不再静默失败。
- 旧存档不做数值迁移、也不改变征收金额：`DensityTax_*` 一律按"相对基础税率的差值"解释。存档版本号（3）无法区分 1.8.7 之前与 1.8.7–1.8.10 写出的档，统一减去基础税率会把后者再减一次，所以不迁移。直接解释是自洽的：面板行显示 `基础 + 差值` 即该档合计税率，本系统收的金额与 1.8.7 之前一致。存档标记升到 4，字段布局不变。
- 税收面板补丁改为按字段惰性解析并逐字段降级，不再因为一个私有字段改名丢掉全部六处集成；补丁失败改用 Error 级别记录。
- 滑块事件只标脏，改由下一个 UIUpdate 帧统一重算预估；此前每次事件都同步跑一次约 15ms 的全城扫描。
- `ZoneDensityCatalog` 的失效判据改为"间隔 ≥5s 且 prefab 数增加"，普查日志收进调试开关；此前资产流式加载会让目录约每 26 秒重建一次并刷两行 INFO。

1.8.6 统一原生住宅基础税率与五类住宅附加税：五类行显示基础税率加本类附加值，调整附加税时保存相对基础税率的差值；基础税率改变时立即刷新五类行和预估。

1.8.5 在密度税率滑块事件中立即执行一次预估并同步刷新密度行、住宅小计和总计，避免原生税收行即时变化而五类住宅行等待后台预估刷新。

1.8.4 将免税线政策图标改为原生 `Policies/` 资源，恢复城市政策列表标准的绿色启用、灰色未启用方框样式。

1.8.3 将设置变化后的预估刷新最小间隔从 100ms 降到约一帧（16ms），让数字变化跟随原生 UI 更新节奏；稳定状态仍按 1 秒或 1024 模拟帧节流。

1.8.2 修复密度税率、免税线或福利设置改变后预估缓存未主动失效的问题。暂停和运行时均在 UI 更新阶段检测变更；连续拖动按最小 100ms 间隔合并重算，设置不变时最多每秒重算一次（模拟推进 1024 帧也可提前触发，但仍受 100ms 限制）。重算后同步刷新五类明细、住宅小计和税收总计。暂停时预估直接使用当前设置的免税线；分类金额用 64 位累加，显示超出整数范围时截断到边界，避免溢出导致正负号翻转。

预估仍基于住户昨日工资、免税线、税率和福利规则，不是实时余额，也不会在刷新时扣款或发钱。因此税基和设置未变时，反复刷新得到相同数字是正常的；改变有应税住户的类别税率后仍长期不变则不正常。构建和逻辑回归不代替游戏内验证。

1.8.1 修正原生 `Locked` 可启停组件的判断：存在组件不代表仍锁定，禁用该组件即为已解锁。该错误会同时导致住宅需求归零、因素隐藏以及工具栏住宅项消失。存档加载完成后重新计算快照，避免暂停时保留加载前的数据。新增标题统一带“需求”，因素列表与原生一致最多五项。未强制拉高需求或跳过真正的解锁条件。

## 实现范围

- 低密度、联排、中密度、高密度、廉租分别统计住房总量、空置住房和解锁状态，分别计算 0–100 的需求。
- 复用原生幸福感、就业、教育、无家可归、基础税率等需求因素；联排沿用中密度的因素模型，廉租沿用高密度的因素模型，但空置量和附加税不再合并。
- 五类需求在原生选址任务中分别使用；每类只允许匹配本类分区的建筑候选。原生建楼、地块尺寸、地价、污染、施工及全城住宅建楼节奏保持不变。
- 删除旧的生成后随机删楼系统。允许某类住宅需求上升时参与选址，不再受另外一类住宅需求为零的限制；道路、地块、解锁、候选建筑等原生条件仍必须满足。
- 未识别名称的住宅分区按原生密度归入低/中/高；混合住宅保留在原生中密度类别，避免遗漏住房供给。
- 工具栏、悬浮图例、需求详情页使用相同五类数据和原生界面组件。每类住宅的空置因素和附加税因素分别显示。
- 为读取原生三槽数据的其他系统保留兼容投影：低；联排/中密度最大值；高密度/廉租最大值。此投影不用于本模组的五类刷楼决策。
- 这是模组扩展的五类需求，并非修改游戏原生 `int3` 的内存布局，也不新增五套重复的全城模拟系统。

## 必须进行的游戏验证

1. 通过 PDX Mods 更新后完全重启游戏，用另存的测试存档验证；确认日志同时出现 `five-density UI binding registered`、`Five-density demand 1.8.11 ready` 和前端 `five residential demand sections`，没有调度兼容错误。已解锁城市的诊断应显示 `unlocked True/True/True/True/True`；真实需求为零仍应保留已解锁类别的工具栏底槽、图例及因素。
   - 1.8.11 重复征收修复：把五类附加税全设为 0，诊断里的"各档合计"与面板五行的预估都应恒为 0——此前这五行会再收一遍基础住宅税率，与原文不一致。
   - 1.8.11 免税线：打开政策并拖动滑块，日志应依次出现 `住宅免税线已生效：<值>（原版 <原版值>）` 与 `住宅免税线写入校验通过：<值>`；关闭政策应出现 `住宅免税线已还原为原版值：<原版值>`。若出现 `住宅免税线写入未生效` 的 WARN，说明经济参数被其它系统覆盖，请把该行日志发回来。
   - 1.8.11 旧档：用 1.8.7 之前的存档读档，五行显示值会比存档时多出一个基础税率（这是 `基础 + 差值` 的正确显示），但征收金额应与升级前一致，不应出现新增补贴。
2. 确认需求页显示低/联排/中/高/廉租五行，工具栏和图例显示相同的已解锁类别；未解锁类别不得提前长楼。
3. 分别调整五种附加税，检查只改变对应类别的税率需求修正；暂停期间数值也应刷新，恢复模拟后由同一组数值控制选址。
4. 在联排为正而中密度为零、廉租为正而高密度为零时，提供满足原生条件的道路和空地，验证联排/廉租仍可新建。反向设零时，仅对应类别停止参与正常新建。
5. 增加某类空置住宅后检查该类需求下降，另一类的空置因素不被合并。检查低/中/高住宅、商业、工业及办公正常建设。
6. 读另一存档、返回菜单再读档、启停分密度税后检查状态重置；用有大量住宅的城市检查帧率和日志中的 Job/NativeContainer 错误。
